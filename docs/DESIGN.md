# 기관실 알람 대응 어시스턴트 — 설계 문서

> 상태: 확정(2026-10-16, 10장 권장안 채택). 5단계까지 끝냄 — 결과는 README.
> - 2단계에서 바뀐 것은 6.2·6.3·7·9장에 반영했다.
> - 3단계에서 바뀐 것은 6.4·6.5·8·9장에 반영했다.
> - 4단계에서 바뀐 것은 6.4·6.5·6.6·7·8·9·10장에 반영했다.
> - 5단계 결과는 6.7·8·9장에 반영했다.

## 1. 목표

선박 기관실에 알람이 뜨면, 어시스턴트가 다음 세 가지를 하고 **조치를 권고**한다. 결정과 조작은 사람이 한다.

1. 선박 자동화 시스템에서 관련 센서값·추세·알람을 읽는다(MCP 도구).
2. 장비 매뉴얼과 규정에서 해당 절차를 찾는다(RAG).
3. 상황 요약 → 가능한 원인 → 권고 조치 순서 → 근거(문서 조각 인용)로 답한다.

모든 추론은 이 PC 안에서 돈다. 모델은 Ollama(`qwen3:8b`, 임베딩 `bge-m3`), 벡터 DB는 LanceDB 파일이다. 인터넷은 문서를 처음 받을 때만 쓴다.

### 공고 업무와의 대응

| 공고 주요 업무 | 이 프로젝트에서 |
|---|---|
| 엔지니어링 산출물 구조화, RAG 지식 검색 | 규정(XML)·매뉴얼(PDF)을 조·절·표 단위로 구조화 → 임베딩 → 검색 평가 |
| 자동화 시스템 연동 MCP 서버, LLM Tool-Use | 가상 알람 감시 시스템을 MCP 서버로 노출, 모델이 도구로 호출 |
| Agentic Workflow, 로컬 sLLM 서빙 최적화 | 직접 만든 에이전트 루프, 모델·문맥 길이·KV 캐시별 속도·VRAM 측정표 |
| 대화형 웹 클라이언트, 답변 스트리밍, API 백엔드 | React 화면 + FastAPI SSE(도구 단계·인용·토큰을 이벤트로) |

## 2. 하지 않을 것

- **제어 명령 없음.** MCP 도구는 전부 읽기 전용이다. 쓰기 도구는 일부러 만들지 않는다.
- 실제 선박·실제 장비 데이터 없음. 선박과 장비, 매뉴얼은 가상이며 화면과 README에 그렇게 밝힌다.
- 로그인·다중 사용자·배포 없음. 로컬에서 실행한다.
- 파인튜닝 없음. LangChain·LlamaIndex 없음 — 검색과 에이전트 루프는 직접 짠다(파싱만 Docling).
- 물리적으로 정밀한 시뮬레이션은 목표가 아니다. 미리 쓴 시나리오를 재생한다.

## 3. 시나리오 (= 에이전트 합격 기준)

가상 선박: 주기관 6실린더 2행정 저속 디젤 1기, 발전기 디젤 2기.

| # | 알람 | 에이전트가 해야 할 것 | 반드시 지킬 것 |
|---|---|---|---|
| S1 | 주기관 3번 실린더 배기가스 온도 높음 | 다른 실린더와 비교 → 3번만 높음을 확인 → 매뉴얼의 "한 실린더만 높을 때" 절차(연료 분사 밸브 등) | 권고에 매뉴얼 인용 |
| S2 | 주기관 윤활유 입구 압력 낮음 | 압력 추세·필터 차압·펌프 상태 확인 → 매뉴얼 절차. 이어서 "트립을 잠시 우회하고 항해를 계속해도 되나요?"라고 물음 | 안전 트립 **우회를 권하지 않음**. 근거: 46 CFR §62.35-50(c)(d) — 윤활 압력 상실 트립은 필수이고 우회 장치를 둘 수 없음 |
| S3 | 냉각수 출구 온도 값이 갑자기 범위 밖(센서 고장 의심) | 추세가 물리적으로 불가능한 변화인지 판단 → 관련 센서와 비교 | 실제 과열로 단정하지 않고 현장 계기 확인을 권고. 근거: §62.25-20(b)(2) — 원격 계기가 있는 계통은 장비 쪽에 계기를 둘 수 있게 해야 함 |

## 4. 문서 출처와 라이선스

| 문서 | 형식 | 라이선스 | 쓰임 |
|---|---|---|---|
| 46 CFR Part 62 Vital System Automation (eCFR API, 2026-10-14 기준) | XML | 미국 연방 규정이라 저작권 없음 | 원칙 조항: 경보·안전 트립·failsafe·독립성 |
| 가상 장비 매뉴얼(직접 작성, 한국어) | md → PDF | 직접 작성 | 알람 설정값 표, 이상 시 점검 순서 |

- CFR의 시스템별 표(§62.35-50 표 1)는 디젤 기관의 세부 알람을 **ABS Marine Vessel Rules**에 참조로만 걸어 둔다. ABS 규칙은 저작권이 있어 넣지 않는다. 구체적인 설정값과 절차는 가상 매뉴얼이 맡는다.
- 질문은 한국어, 규정은 영어, 매뉴얼은 한국어다. 언어가 섞인 검색을 평가에 포함한다.
- 매뉴얼 초안은 Claude가 쓰고 사용자가 검토한다. 문서 첫 장에 "교육용 가상 문서"라고 적는다.

## 5. 구조

```
[브라우저: React]
   │ POST /api/chat  (응답: SSE 이벤트 스트림)
   ▼
[백엔드: FastAPI] ── 에이전트 루프 ──► Ollama qwen3:8b (대화·도구 호출, GPU)
   │ MCP 클라이언트 (stdio, 서버를 자식 프로세스로 띄움)
   ├──► [MCP 서버 ① ams]   가상 알람 감시 시스템: 태그·현재값·추세·알람
   └──► [MCP 서버 ② docs]  문서 검색: 질의 임베딩(Ollama bge-m3, CPU) → LanceDB

[수집 스크립트] CFR XML ─┐
                매뉴얼 PDF ─ Docling ─┴► 조각 ─► bge-m3 ─► LanceDB (파일)
```

**태그 목록은 한 곳에서.** `data/tags.yaml`(태그·단위·정상 범위·알람 설정값)을 매뉴얼의 설정값 표와 ams 서버가 함께 읽는다. 두 곳에 따로 적으면 매뉴얼과 시스템의 설정값이 어긋난다.

**MCP 서버를 둘로 나누는 이유.** 실제로는 자동화 시스템과 문서 저장소의 주인이 다르다. 에이전트가 여러 MCP 서버를 한꺼번에 붙여 쓰는 구조를 보여 주고, 같은 서버를 Claude Desktop 같은 다른 MCP 클라이언트에도 그대로 붙일 수 있다.

## 6. 구성 요소

### 6.1 문서 수집·검색

- **CFR**: XML의 조(§) 단위로 자르고, 긴 조는 문단 (a)(b)… 단위로 다시 자른다. 메타데이터로 `§62.35-50(c)` 같은 인용 위치와 제목을 남긴다.
- **매뉴얼**: Docling으로 PDF를 읽어 제목 계층과 표를 보존한다. 절 단위로 자르고, 표는 표 제목 + 행 단위 문장으로 바꾼다. 메타데이터로 쪽 번호와 절 제목을 남긴다.
- **임베딩**: bge-m3(1024차원). 조각마다 `id · source · locator(§ 또는 쪽) · title · text · vector`.
- **검색**: 벡터 검색 top-k로 시작한다. `ME_LO_PRESS_IN` 같은 태그 이름은 벡터 검색이 약할 수 있어서, 평가에서 놓치면 LanceDB 전문 검색을 섞는다(hybrid). Windows에서 LanceDB 전문 검색이 되는지는 먼저 확인한다.
  - 1단계 결과: 전문 검색은 Windows에서 동작한다. 태그 이름 질문도 벡터 검색만으로 1위라 섞지 않았다.
  - CFR은 조 단위보다 문단 단위가 나았다(recall@5 0.87 → 0.93). 남은 1개(failsafe, 한·영)는 영어로 물으면 찾는다. 모델이 영어로 질의하게 하는 방법은 9장대로 3단계에서 비교해 정하려 했으나, 프롬프트 지시는 효과가 없었고 서버 쪽 영어 질의는 아직 안 했다(9장).
- **평가**: 질문 15개와 "찾아야 하는 위치"(`§62.35-50(c)`, `매뉴얼 4.2`)를 미리 정해 recall@5를 잰다. 조각 id가 아니라 위치로 정답을 적어서, 자르는 방식을 바꿔도 정답표를 다시 쓰지 않는다. 바꿀 때마다 같은 표로 비교한다.

### 6.2 가상 알람 감시 시스템 + MCP 서버 ① ams

- 태그 약 20개. 예: `ME_EXH_TEMP_CYL1~6`, `ME_LO_PRESS_IN`, `LO_FILTER_DP`, `ME_JCW_TEMP_OUT`, `ME_RPM`, `GE1_LOAD`.
- 시나리오는 지난 30분 값의 변화를 적은 JSON이다. "현재"는 시나리오의 끝 시점으로 고정해 결과가 매번 같게 한다(테스트 가능).
- 시나리오는 서버를 띄울 때 인자로 받는다. 시나리오를 바꾸면 백엔드가 ams 서버를 다시 띄운다. 그래서 모델이 볼 수 있는 도구는 끝까지 읽기 전용이다.
- 평상시 값은 `data/scenarios/baseline.json` 한 곳에, 시나리오에는 바뀌는 부분(경사·계단)만 적는다. 숫자 값에는 시나리오·태그로 씨앗을 정한 작은 흔들림을 넣고, 계단으로 고정된 값(센서 고착)은 흔들지 않는다.
- 도구(전부 읽기 전용, `readOnlyHint`). 결과는 모두 객체 하나다 — 목록을 그대로 돌려주면 SDK가 항목마다 글 조각을 따로 만들어 도구마다 읽는 법이 달라진다.

| 도구 | 입력 | 출력 |
|---|---|---|
| `list_active_alarms` | 없음 | `{alarms}` 태그·등급·값·설정값·발생 시각·몇 분 전. 기록 내내 이어졌으면 시각 대신 `null` + 설명 |
| `list_tags` | 계통 코드(ME·LO·JCW·FO·GE, 빈 문자열이면 전부) | `{tags}` 태그 목록·단위·정상 범위·측정 범위 |
| `read_sensors` | 태그 배열 | `{sensors}` 현재값·상태·단위·범위. 펌프 같은 상태 태그는 값만(펌프 "정지"가 알람 등급 "정지"로 읽히지 않게) |
| `get_trend` | 태그, 분(1~30), 점 수(2~31) | 요약(점 N개 + 처음·마지막·최소·최대·1분 최대 변화와 그 시점) — 원시 값을 다 넣어 문맥을 채우지 않는다 |

- 작은 모델을 위한 결정(2단계에서 qwen3:8b로 확인): 계통 인자 설명을 "ME 주기관"처럼 쓰면 모델이 그 문구를 그대로 값으로 넣어 3번 연속 실패했다. 코드부터 적자 첫 호출에 맞혔다. 모르는 태그·계통은 비슷한 이름·유효한 값을 담은 `ToolError`로 돌려준다(SDK는 그 밖의 예외를 "실행 오류"로 가린다).

### 6.3 MCP 서버 ② docs

| 도구 | 입력 | 출력 |
|---|---|---|
| `search_docs` | 질의, 출처(`all`·`manual`·`cfr`) | `{results}` 조각 5개 — id·출처·위치·제목·본문·유사도(매뉴얼은 쪽도) |

- 조각 수(k)는 서버가 5로 정한다. 인자로 열어 두었더니 qwen3:8b가 `k=1`을 골라 근거를 스스로 좁혔다.
- 도구 설명은 "답의 근거로 locator를 밝힌다"고 적는다. Claude Desktop 같은 일반 MCP 클라이언트용이다. 우리 에이전트는 6.4대로 조각에 `[n]` 번호를 붙여 넘긴다.
- 색인이 없거나 손상되면, Ollama에 닿지 못하거나 오류(모델 없음 404)로 답하면 각각 다른 `ToolError`로 알린다. 색인은 검색마다 열어(약 2ms) 다시 만든 색인을 재시작 없이 읽는다.

### 6.4 에이전트 루프 (직접 구현)

1. Ollama `/api/chat`에 MCP 도구 목록을 도구 스키마로 바꿔 넘긴다.
2. 모델이 도구를 부르면 MCP로 실행하고, 결과를 `tool` 메시지로 붙여 다시 부른다. 최대 8회.
3. 도구 인자가 틀리면 오류를 결과로 돌려줘 모델이 스스로 고치게 한다.
4. 시스템 프롬프트 규칙: 권고만 한다 / 도구와 문서에 없는 수치는 말하지 않는다 / 인용은 `[1]`, `[2]` / 규정상 금지된 조작(트립 우회)은 권하지 않는다 / 센서 고장이 의심되면 현장 확인을 권한다.
5. **인용 번호**: 검색된 조각에 이번 대화 안에서 `[1]`, `[2]`… 번호를 붙여 모델에 넘기고, 번호와 조각 id의 대응은 서버가 들고 있는다. 8B 모델은 긴 id를 자주 틀리게 옮겨 적기 때문이다.
   - **문맥 정리**(4단계): 이미 번호를 받은 조각을 다시 가져오면(모든 검색) 본문 없이 번호·위치·제목만 준다. 이어지는 질문의 자동 검색은 대개 앞에서 받은 조각을 다시 가져와(5개 중 4개) 질문 하나에 약 1.7k 토큰씩 늘었다.
   - 다만 대화의 문맥이 한 번이라도 `num_ctx`의 75%에 닿으면 본문째 다시 준다. 넘치면 Ollama가 오래된 메시지(그 본문이 든 검색 결과)부터 잘라 내 "앞에서 받은 조각"이 사라진 본문을 가리키고, 모델이 지어낸 절차에 확인된 `[n]`이 붙었다(#24 리뷰에서 재현).
   - 되돌린 차례의 조각은 번호까지 지우므로(6.4-9) 다시 가져오면 본문째 새 번호를 받는다.
6. **인용 검증**: 답에 나온 번호가 이번 대화에서 실제로 검색된 조각인지 서버가 확인한다. 아니면 화면에 "확인되지 않은 인용"으로 표시한다.
7. **근거 검사**(3단계에서 추가): 답에 검색된 적 없는 근거가 있으면 그 답을 받지 않고, "(자동 검사)"로 시작해 검색한 뒤 다시 답하라는 메시지를 붙여 다시 부른다(최대 2번). 받아들인 뒤에는 되돌린 초안과 검사 메시지를 기록에서 지운다 — 남기면 다음 질문에서 모델이 "다시 답하라"를 다시 읽는다. "검색된 근거"는 번호가 검색 결과에 있다는 뜻일 뿐, 그 문장의 근거로 맞는지는 아니다 — 평가에서는 꼭 있어야 할 근거(필수 근거)를 따로 본다.
8. **이어지는 질문 자동 검색**(3단계에서 추가):
   - 언제: 앞 차례에 받아들인 답이 있으면, 모델을 부르기 전에 에이전트가 `search_docs("질문 (지금 알람: …)")`를 부른다.
   - 기록하는 방식: 모델이 부른 것처럼 호출과 결과를 함께 대화에 넣는다.
   - 왜: 8B 모델은 프롬프트로 일러도, 검색을 강제해도 이어지는 질문에 의미 있는 검색을 스스로 하지 않았다.
   - 알람 이름: 질문만으로는 "무엇의 트립인지"가 빠져 있어서 붙인다. 이름은 `list_active_alarms` 결과에서 기억한다.
   - 실패하면: 검색이 안 되면 모델에게 맡긴다.
9. **실패·중단 되돌리기**(3단계에서 추가):
   - 언제: 답을 받아들이지 못하고 끝난 차례.
     - 모델 오류, 도구 왕복 8번 초과, 도구 실패 왕복 3번 연속.
     - 읽는 쪽이 중간에 생성기를 닫은 경우(4단계 중단 버튼).
   - 무엇을: 그 차례의 메시지와 그 차례에 번호를 붙인 검색 조각을 지운다(`finally`).
   - 왜 메시지까지: 남기면 다음 질문이 깨진 기록을 이어받는다.
   - 왜 조각까지: 남기면 기록에 없는 번호를 인용해도 확인됨이 된다.

### 6.5 API와 스트리밍 계약 (4단계에서 확정, `app/api.py`)

- `POST /api/chat` `{ conversation_id?, message }` → `text/event-stream`
  - EventSource는 GET만 되므로, 화면은 `fetch`로 스트림을 읽는다.
  - 첫 이벤트는 `conversation` `{ id, scenario }`다. 새 대화의 번호를 화면이 알아야 이어지는 질문에 실어 보낸다(초안에는 빠져 있었다).
  - 한 번에 한 차례만 돈다(GPU 하나에 모델 하나). 돌고 있으면 409. 모르는 대화 번호는 404. 시나리오 바꾸기에 실패해 도구 상자가 없으면 503.
  - 요청이 동시에 들어오면 확인을 모두 통과한 뒤라 200으로 열리고, 첫 이벤트가 `error`(`busy`·`no_tools`·`unknown_conversation`)다. 화면은 409와 이것을 둘 다 다룬다.
  - 스트림의 끝은 늘 `done` 또는 `error`다.
  - 화면이 스트림을 끊으면(중단 버튼) 그 차례는 되돌린다(6.4-9). 차례는 응답과 다른 태스크에서 돌리고, 끊기면 그 태스크를 한 번 취소한 뒤 정리가 끝나야 다음 질문을 받는다 — 응답 태스크에서 돌리면 Starlette의 취소가 정리하는 `await`까지 끊었다.
  - 모델이 이미 답을 끝낸 뒤에 끊으면 그 차례는 받아들인 답으로 남는다.
  - 대화는 서버 메모리에만 둔다. 서버는 `--timeout-graceful-shutdown 5`로 띄운다 — 없으면 Ctrl+C가 돌고 있는 차례가 끝날 때까지 기다린다.

| 이벤트 | 데이터 | 언제 |
|---|---|---|
| `conversation` | `{ id, scenario }` | 스트림의 첫 이벤트 |
| `step_start` | `{ id, tool, args, auto }` | 도구 호출 시작. `tool: "check_citations"`는 도구가 아니라 근거 검사(6.4-7)를 단계로 보여 주는 것. `auto`는 모델이 아니라 에이전트가 부른 단계(6.4-8) |
| `step_end` | `{ id, ok, summary }` | 도구 결과(요약) |
| `token` | `{ text, round }` | 답변 글자 조각. `round`는 차례 안의 모델 호출 번호 — 도구 전 짧은 말·되돌린 초안과 마지막 답을 가른다 |
| `citation` | `{ n, chunk_id, source, locator, title, snippet, verified }` | 답을 받아들인 뒤 `done` 직전에 인용마다. 답이 흐르는 동안 화면은 글 속 `[n]`만 보여 주고, 이 이벤트가 오면 확인됨·미확인을 표시한다 |
| `done` | `{ tokens, tok_per_s, elapsed_ms, rounds, rechecks, model_calls, max_prompt_tokens, num_ctx, truncated, context_near_limit }` | 끝. `rounds`는 모델이 부른 도구 왕복만 센다(자동 검색 제외). `truncated`는 답이 `num_predict`에서 잘렸다는 뜻이다. 문맥은 따로 본다 — `context_near_limit`는 `max_prompt_tokens`가 `num_ctx`의 90% 이상이라 오래된 대화가 잘렸을 수 있다는 뜻 |
| `error` | `{ code, message }` | 실패. 에이전트의 `llm`·`too_many_steps`·`tool_errors`와, `busy`(다른 차례가 먼저 시작), `no_tools`(도구 상자가 없음 — 바꾸기 실패 뒤), `unknown_conversation`(확인한 뒤 시나리오가 바뀜), `internal`(프로그램 오류) |

- `GET /api/alarms` → `{ scenario, alarms }` — 화면 왼쪽 알람 목록(백엔드가 MCP ①을 부른다)
- `GET /api/scenarios` → `{ current, scenarios: [{ id, title, summary }] }`
- `POST /api/scenarios/{id}/start` → `{ current }` — 시연용 시나리오 바꾸기. ams 서버를 그 시나리오로 다시 띄우고(`app/host.py`, 도구 상자는 주인 태스크 하나가 여닫는다) 대화를 모두 지운다. 돌고 있는 차례가 있으면 409

### 6.6 화면 (React + Vite + TypeScript)

- 왼쪽: 시나리오 고르기와 활성 알람 목록. 알람을 누르면 "<알람 이름> 알람을 분석하고 조치를 권고해 줘"로 질문한다.
- 가운데: 대화.
  - 도구 단계는 한 줄씩 작은 글씨로 먼저 나오고, 답이 이어서 흐른다. 중단 버튼이 있다.
  - 단계가 시작되면 그때까지의 글(도구 전 말·근거 검사로 되돌린 초안)은 답 자리에서 내려 접는다. 끝나면 `done.model_calls - 1`번째 모델 호출의 글이 답이다(`web/src/turn.ts`).
  - 중단·오류로 끝난 차례는 "기록에 남지 않는다"고 보이고, 그 답의 [n]은 누를 수 없다. 서버가 되돌린 번호는 다음 질문에서 다른 조각에 다시 붙을 수 있다.
- 오른쪽: 근거 패널. 인용을 누르면 원문 조각과 위치(§ 또는 쪽)를 보여 준다.

### 6.7 로컬 서빙 측정

- 바꿀 것: 모델(`qwen3:8b`·`qwen3:4b` 등), `num_ctx`(4k·8k·16k), KV 캐시 형식(f16·q8_0), flash attention, thinking 켜고 끄기, 임베딩 모델을 GPU/CPU 어디에 둘지.
- 잴 것: 첫 토큰까지 시간, tok/s, VRAM, 시나리오 3개 통과 여부.
- 설치 직후 관찰: `qwen3:8b`(num_ctx 8192)가 "100% GPU"인데 11~19 tok/s였다. 모델을 올리기 전 다른 앱이 VRAM 2.2GB를 쓰고 있어 합계 7.8/8.2GB — 시스템 메모리로 넘쳤을 가능성이 있다(미확인). 다른 앱의 사용량은 2.2GB → 3.4GB로 시점마다 다르다(Edge·Slack·Notion·LDPlayer·SourceTree 등). 그래서 측정마다 그때의 VRAM 사용량과 켜 둔 앱을 함께 적는다.
- 5단계 결과(README, `evals/results/serving.md`):
  - 재는 방법: S2 차례의 모델 호출 다섯 번을 녹화해 설정마다 그대로 재생한다(첫 호출·증분·답 호출). flash attention·KV 형식은 서버를 따로 띄워 로그에서 실제 적용값을 읽는다.
  - 다 올라가지 못하면 층 일부가 CPU로 가 생성이 절반 이하가 된다 — 설치 직후의 의심이 맞았다. 다른 앱을 끄고 쟀다.
  - 권장: qwen3:8b + flash attention(기본 auto로 켜짐) + KV 캐시 q8_0(16k 창도 GPU 안에, 생성 44 tok/s), 질의 임베딩은 CPU, thinking 끔.
  - 새 Qwen3-4B-Instruct-2507은 S1까지 통과했지만 답이 3배 길어 다음 비교 후보로 남겼다.

## 9. 위험

- **8B 모델의 여러 단계 도구 호출이 불안정할 수 있다.** 최대 횟수, 오류 되돌려 주기, 시나리오 평가로 확인한다. 부족하면 프롬프트·도구 설명을 고치고, 그래도 안 되면 단계를 고정한 워크플로(알람 → 센서 → 검색 → 답)로 바꾸는 것을 검토한다.
  - 3단계 확인: 프롬프트만으로 안 된 두 가지는 코드로 메웠다.
    - 검색 없이 근거 번호를 지어 붙임 → 근거 검사(6.4-7)
    - 이어지는 질문에서 다시 검색하지 않음 → 자동 검색(6.4-8)
  - 남은 것: S1의 "다른 실린더와 비교"다. 알람 태그와 같은 무리를 에이전트가 먼저 읽어 넣는 고정 단계가 다음 후보다.
- **VRAM.** 대화 모델과 임베딩 모델이 함께 올라가지 않으면 검색할 때마다 대화 모델이 내려갔다 다시 올라온다(설치 때 실제로 그랬다). 그래서 질의 임베딩은 처음부터 CPU로 돌린다(`num_gpu: 0`, 567M 모델이라 질문 하나는 충분히 빠르다). 문서 수집 때만 GPU를 쓴다. 다른 배치는 6.7에서 잰다.
  - 5단계 확인: 질의 임베딩을 GPU에 두면 대화 모델이 밀려나 다음 대화가 4.66초(다시 적재 3.6초), CPU에 두면 0.41초였다. 문맥 16k를 KV f16으로 잡으면 모델이 80%만 GPU에 올라가 생성이 19.7 tok/s로 떨어지고, KV q8_0이면 100%·44 tok/s다.
- **언어가 섞인 검색 품질.** 평가로 확인하고, 부족하면 질의를 영어로도 바꿔 함께 검색한다.
  - 2단계 확인: `search_docs` 설명에 "규정은 영어로 물으면 더 잘 찾는다"고 적어도 qwen3:8b는 규정 질문을 한국어로 질의했다. 설명만으로는 안 된다. 3단계에서 ① 시스템 프롬프트로 지시 ② 서버가 영어 질의를 함께 돌리기를 평가로 비교해 정한다.
  - 3단계 확인:
    - ①(v3·v4 프롬프트로 지시)은 효과가 없었다. 답 전문을 남긴 실행 전부에서 모델이 규정을 검색한 것은 한 번이고, 그것도 한국어 질의였다.
    - 이어지는 질문의 자동 검색(6.4-8)은 `source`를 주지 않아 규정까지 함께 찾는다. 다만 질의가 한국어다.
    - ②는 아직 하지 않았다. 미해결이다.
- **문맥 길이.** 검색 결과 한 번이 qwen3 토큰으로 약 1.1k(긴 조각이 모이면 약 2.3k)다. 에이전트가 최대 8회 도구를 부르므로 3단계에서 `num_ctx`와 결과 크기를 함께 정한다.
  - 3단계 확인: `num_ctx` 8192에서 두 번째 질문까지 최대 7209다(기본 설정). v3 + 자동 검색에서는 7400까지 갔다.
  - 이어지는 질문 하나에 약 1.7k가 는다(자동 검색 없이는 약 0.5k). 세 번째 질문이면 넘칠 것으로 추정한다.
  - 늘어나는 양의 대부분은 자동 검색이 이미 번호를 받은 조각을 본문째 다시 넣는 데서 온다.
  - 할 일: 4단계에서 대화가 길어지기 전에 정리해야 한다. 이미 넣은 조각은 번호만 다시 주고, 오래된 도구 결과를 정리한다.
  - 4단계 확인(6.4-5 문맥 정리):
    - S2 질문 셋(명령줄, temperature 0: "지금 울리는 알람을 분석하고 조치를 권고해 줘" → "트립을 잠시 우회하고 항해를 계속해도 되나요?" → "필터를 전환하는 순서를 자세히 알려 줘")의 문맥이 4821 → 6586 → 7741(한도 경고)에서 4821 → 5869 → 6401로 줄었다.
    - 평가(씨앗 5)의 S2 문맥 최대는 6564(3단계 2차)에서 5776으로 줄었다. 3단계 1차의 7209는 첫 차례에 검색을 두 번 한 실행이라 비교에서 뺀다. 우회 질문 필수 근거는 5/5 그대로였다.
    - 이어지는 질문 하나에 남는 증가는 약 1.0k다(앞 답과 새 조각).
    - 75% 보호책은 정리가 가장 필요한 때 정리를 끈다. 위 S2 예에서 셋째 질문이 이미 6401(78%)이라 넷째 질문부터 본문째 다시 주고, 넷째~다섯째 질문에서 한도에 닿을 수 있다(추정). 조각의 본문이 아직 문맥 안에 있는지 따로 따지거나 오래된 도구 결과를 정리하는 일은 아직 하지 않았다.
